# CodeShuttle

Перенос кода проекта между машинами текстовыми батчами. Жмёшь кнопку — весь код
проекта режется на `.txt` файлы по 45 КБ, из которых вычищены пароли, ключи и
токены. На другой машине жмёшь другую кнопку — батчи раскладываются обратно в
дерево файлов, каждый в свою папку.

Дальше работаешь, что-то меняешь — жмёшь «Выгрузить только изменения», и в
один маленький батч уезжают именно те 3 файла, что поменялись (плюс список
удалённых). Приёмник их подменяет.

Если в выгружаемой папке лежат git-репозитории, одна кнопка
**«ЭКСПОРТ ОДНОЙ КНОПКОЙ: git fetch → батчи → .rar»** сначала подтягивает в них
нужные ветки с remote (там, где лежит файл ветки `.codeshuttle-branch.json`),
а потом выгружает всё батчами и пакует в один `.rar`. Подробности — в разделе
[«Экспорт одной кнопкой»](#экспорт-одной-кнопкой-git--батчи--rar).

**Требуется:** только Python 3.9+ (у тебя стоит 3.14). Никаких зависимостей,
никакой сборки. Язык твоего проекта значения не имеет — Java, Python, JS и
прочее переносятся одинаково.

---

## Быстрый старт

### На машине-источнике (A)

1. Скачал репозиторий, двойной клик по **`start.bat`** — откроется окно.
   При первом запуске рядом появится `config.json` (копия `config.example.json`);
   он в `.gitignore`, потому что пути у каждой машины свои.
2. Сверху указал **корень проекта** — папку, которую выгружаем (это может быть
   и папка с несколькими репозиториями).
3. Вкладка **«⬆ ЭКСПОРТ»**: указал **папку батчей (outbox)** и, если нужно,
   **папку архивов .rar**.
4. Нажал зелёную **«⬆ ЭКСПОРТ ОДНОЙ КНОПКОЙ»** — в папке архивов появился
   `<время>_<проект>_full.rar` с батчами внутри. Батчи лежат и в outbox:
   `20260902T104500-a1b2c3_full_batch_001_of_012.txt`, отчёт — в `outbox/_reports/`.

Без архива: в блоке «Вручную, без git» кнопка **«Весь проект → батчи»**.

### На машине-приёмнике (B)

1. Тот же репозиторий, `start.bat`.
2. Сверху — **корень проекта** (куда раскладывать), вкладка **«⬇ ИМПОРТ»** —
   **папка с батчами (inbox)**.
3. Прислали `.rar` — **«Распаковать архив .rar в inbox и применить…»**.
   Прислали `.txt` — положил их в inbox и нажал синюю
   **«⬇ ИМПОРТ: применить батчи из inbox к проекту»**. Все папки и файлы созданы.

### Дальше — только изменения

На отправителе переключатель «Что выгружать» → **«только изменения с прошлой
выгрузки»** и та же зелёная кнопка (или «Только изменения → батчи» без git) →
на приёмнике синяя кнопка. Синхронизация двусторонняя: после импорта приёмник
сам умеет слать дельты обратно.

## Что именно выгружается

**Выгружается:** исходники и текстовая конфигурация (`.java`, `.py`, `.js`,
`.ts`, `.go`, `.sql`, `.md`, `.xml`, `.json`, `.properties`, `.yaml`,
`.gradle`, `Dockerfile`, `Makefile`, …) — полный список в `config.json` →
`scan.extensions`. Плюс сборочные дескрипторы из `scan.keep_globs`
(`pom.xml`, `package.json`, `pyproject.toml`, `Cargo.toml`, …) — они нужны,
чтобы проект на приёмнике собрался.

**Не выгружается никогда:**

| Категория | Примеры |
|---|---|
| Мусор сборки | `node_modules/`, `target/`, `build/`, `dist/`, `.gradle/`, `__pycache__/`, `.venv/` |
| Бинарники и медиа | `*.class`, `*.jar`, `*.png`, `*.zip`, `*.db`, всё, что не декодируется в UTF-8 |
| Слишком большие файлы | файлы крупнее `scan.max_file_kb` |

CodeShuttle не анализирует и не изменяет содержимое файлов. Строки, похожие на
пароли, токены, ключи, внутренние URL или длинные идентификаторы, передаются
дословно. За состав выгрузки отвечают только обычные фильтры `scan`.

После каждой выгрузки создаётся отчёт `_reports/report_<пак>.md`: сколько
батчей сформировано и какие файлы пропущены техническими фильтрами.

## Формат батча

Обычный текст, читаемый глазами и безопасный для копипаста:

```
### CODESHUTTLE 1
### PACK 20260902T104500-a1b2c3
### KIND delta
### BATCH 2 OF 7
### BASE 5f2c…            отпечаток дерева, от которого считалась дельта
### RESULT 9ab1…          отпечаток дерева после применения
### GENERATED 2026-09-02T10:45:00Z
### ---
--8<-- BEGIN {"path":"src/main/java/app/Main.java","part":1,"parts":1,"bytes":812,"sha256":"…","nonl":0}
package app;
public class Main { }
--8<-- END
--8<-- DELETE {"path":"src/old/Legacy.java"}
```

Гарантии:

- **Целостность.** У каждого файла свой `sha256`; при импорте он проверяется, и
  пак с расхождением не применяется целиком, а не наполовину.
- **Полнота.** `BATCH k OF n` — импорт откажется применять пак, если хоть один
  батч не донесли.
- **Точность.** Файл восстанавливается байт в байт: пустые файлы, отсутствие
  перевода строки в конце, UTF-8, табы. Строки, которые сами начинаются с
  `--8<--`, экранируются и парсер их не путает с разметкой.
- **Большие файлы.** Файл больше лимита режется на части (`part 2/5`), в том
  числе если это одна строка на 100 КБ. Склейка проверяется хэшем.
- **Мусор вокруг не мешает.** Парсер вытаскивает батчи даже из файла, где
  вокруг налеплен посторонний текст, и понимает несколько батчей в одном файле.

## Окно

Сверху — **корень проекта** (общий для обеих вкладок), внизу — журнал.
Посередине две вкладки: на машине-отправителе живёшь в «Экспорте», на
приёмнике — в «Импорте». Окно помнит, какая вкладка была открыта.

### Вкладка «⬆ ЭКСПОРТ — отправить отсюда»

| Элемент | Что делает |
|---|---|
| **⬆ ЭКСПОРТ ОДНОЙ КНОПКОЙ: git fetch → батчи → .rar** | Git-подготовка папок с файлом ветки, затем выгрузка и упаковка батчей в `.rar`. См. раздел ниже. |
| Что выгружать: **весь проект / только изменения** | Что положить в архив: полный пак или дельту с прошлой выгрузки. |
| **спрашивать перед переключением веток** | Перед `checkout` на другую ветку показать план и спросить «да/нет». |
| Таблица **«Папки проекта»** | Папки с файлом ветки (ветка, текущая ветка, что будет) и папки без него («как есть»). Цвет: зелёный — готово, синий — будет переключено/обновлено, жёлтый — есть предупреждения, красный — проблема. |
| **Проверить ветки (fetch, ничего не меняя)** | fetch + все проверки, результат — в таблице и журнале. Рабочие копии не трогаются. |
| **Файл ветки для папки…** / двойной щелчок по строке | Диалог: создать, поправить или удалить `.codeshuttle-branch.json`. Ветку можно выбрать из списка веток remote. |
| **Вручную, без git** | Старые кнопки: «Весь проект → батчи», «Только изменения → батчи», «Изменения → батчи → .rar», «Что изменилось?», «Отметить текущее как синхронизированное». Git здесь не трогается — все папки уходят как есть. |

### Вкладка «⬇ ИМПОРТ — принять сюда»

| Кнопка | Что делает |
|---|---|
| **⬇ ИМПОРТ: применить батчи из inbox к проекту** | Читает inbox, проверяет суммы, раскладывает файлы. |
| **Распаковать архив .rar в inbox и применить…** | Выбираешь присланный `.rar` — он распаковывается в `inbox/<имя архива>/` (Rar.exe/UnRAR.exe из WinRAR, иначе `tar` из Windows 11) и сразу применяется. |
| **Выбрать другую папку с батчами и применить…** | То же, но папку выбираешь диалогом прямо сейчас (она же запоминается в конфиг). |
| **Проверить без записи** | Отчёт: что было бы создано, обновлено и удалено. |

Импорт сразу применяет изменения к проекту и не создаёт резервных копий.
Полностью применённые паки уезжают в `inbox/_applied/<пак>/`.

## Экспорт одной кнопкой (git → батчи → .rar)

Корень проекта может быть папкой с несколькими репозиториями. Для каждого
репозитория, который нужно выгружать **с определённой ветки remote**, в его
корень кладётся файл ветки **`.codeshuttle-branch.json`**:

```json
{
  "branch": "release/2026.10",
  "remote": "origin",
  "checkout": "auto",
  "allow_dirty": false,
  "enabled": true
}
```

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `branch` | — (обязателен) | Ветка на remote, с которой выгружать. |
| `remote` | `origin` | Откуда fetch. |
| `checkout` | `auto` | `auto` — CodeShuttle сам переключит репозиторий на ветку; `manual` — не переключает, а останавливает выгрузку и просит переключить самому. |
| `allow_dirty` | `false` | `true` — разрешить незакоммиченные правки, если они не конфликтуют с веткой (тогда они уедут в выгрузку). |
| `enabled` | `true` | `false` — файл есть, но папка выгружается как есть. |

Проще всего создавать файл из окна (двойной щелчок по папке в таблице) или
командой `python -m codeshuttle git-mark <папка> <ветка>`. Файл достаточно
написать и одной строкой — просто именем ветки. При создании из окна/командой
он дописывается в `.git/info/exclude`, чтобы не светиться в `git status`.
В выгрузку сам файл ветки не попадает.

Папки **без** файла ветки git не трогает: они выгружаются как есть, как и раньше.
Пример: в корне 10 репозиториев, в 5 из них лежит файл ветки — эти 5 сначала
подтягиваются с remote на свои ветки, остальные 5 уходят в том состоянии, в
котором лежат на диске.

### Что происходит по шагам

1. **Проверка — во всех папках с файлом ветки, ничего не меняя.**
   `git fetch <remote> <ветка>` (обновляет только `refs/remotes/…`), затем:

   | Проверка | Итог |
   |---|---|
   | папка не git-репозиторий, нет такого remote | ошибка |
   | **ветки нет на remote** | ошибка |
   | незавершённый merge / rebase / cherry-pick / revert / bisect, `index.lock` | ошибка |
   | неразрешённые конфликты в рабочей копии | ошибка |
   | **незакоммиченные изменения** в отслеживаемых файлах | ошибка (при `allow_dirty: true` — предупреждение) |
   | **конфликт при переключении/обновлении**: у тебя изменён файл, который отличается и в ветке remote | ошибка всегда, файлы названы поимённо |
   | неотслеживаемый файл, который ветка перезаписала бы | ошибка |
   | в локальной ветке есть незапушенные коммиты / ветка разошлась с remote | ошибка |
   | `checkout: manual`, а репозиторий на другой ветке | ошибка «переключи сам» |
   | прочие неотслеживаемые файлы | предупреждение (уедут как есть) |

2. **Хоть одна ошибка хоть в одной папке — стоп.** Ни одна ветка не
   переключается, батчи не создаются, окно показывает список причин.
3. **Подтверждение.** Если какой-то репозиторий нужно переключить на другую
   ветку, окно показывает план («admin-panel: main → develop», «report-processor:
   release/1.4 +3») и спрашивает. «Нет» — ничего не трогается, можно
   переключить руками и нажать кнопку снова. Выключается галочкой
   «спрашивать перед переключением веток».
4. **Переключение.** Для каждой папки ещё раз проверяется, что с момента проверки
   ничего не поменялось, затем `git checkout -B <ветка> <remote>/<ветка>`
   (другая ветка) или `git merge --ff-only` (та же ветка, remote ушёл вперёд).
   Только fast-forward: локальные коммиты не теряются, потому что при их
   наличии проверка на шаге 1 уже остановила бы выгрузку.
5. **Выгрузка и архив** — штатный экспорт (весь проект или изменения) и `.rar`,
   как в разделе ниже. Репозитории остаются на своих ветках.

## Откуда берётся «изменено»

Это нужно **только экспорту**. При каждом экспорте и импорте CodeShuttle
записывает слепок `.state/state_<хэш пути проекта>.json` — в нём `путь -> sha256`
всех файлов кода на тот момент. При следующем экспорте суммы считаются заново
и сравниваются со слепком:

- нет в слепке, есть на диске → **новый**;
- есть в обоих, sha разные → **изменённый**;
- есть в слепке, нет на диске → **удалённый**.

Слепок лежит рядом с инструментом, привязан к пути проекта, у каждой машины
свой и в git не едет. Кнопка «Отметить как синхронизированное» просто
перезаписывает его текущим состоянием — после неё дельта будет пустой.

**Импорт к слепку не привязан вообще.** Он сравнивает то, что приехало в
батче, с тем, что реально лежит на диске:

| На диске | Действие |
|---|---|
| файла нет | создать (вместе со всеми папками по пути) |
| есть, sha не совпал | обновить |
| есть, sha совпал | не трогать (даже mtime не меняется) |
| пришёл `DELETE` | удалить |

## Что гарантируется при «свалил всё в папку и применил»

Имена файлов батчей не важны — всё берётся из заголовков внутри. Проверено
тестами (`selftest_import.py`):

- **дубликаты.** Один и тот же батч, лежащий в папке в трёх копиях под разными
  именами, применяется один раз;
- **повторный запуск.** Те же батчи, применённые второй раз, дают ноль
  изменений — операция идемпотентна;
- **порядок.** Батчи и паки читаются в любом порядке. Порядок применения
  восстанавливается по времени пака, а поверх — по цепочке состояний:
  дельта не может лечь раньше пака, чьим `RESULT` является её `BASE`;
- **full и delta вперемешку.** Сваливай оба в одну папку: применятся по
  порядку, победит более свежая версия файла;
- **неполный пак.** Файлы, которые собрались целиком и сошлись по sha,
  применяются; недостающие называются поимённо. Удаления откладываются, пока
  пак не доедет полностью. Донёс недостающий батч, нажал снова — доложилось.
  Нужно строгое «всё или ничего» — поставь `import.require_all_batches: true`;
- **порченый батч.** Файл с несошедшейся суммой не пишется вообще — половина
  файла в проект не попадёт.

## Батчи одним архивом (`archive`)

Обёртка над обычной выгрузкой — для случая «перекинуть себе код через чат,
куда файлы .txt по одному не наотправляешься». Её же вызывает экспорт одной
кнопкой после git-подготовки; команда `archive` — то же самое без git:

```bash
python -m codeshuttle -c config.<модуль>.json archive
```

```bash
python -m codeshuttle -c config.<модуль>.json archive --full --dry-run
```

Что делает по шагам:

1. **чистит outbox** — удаляет `*.txt` прошлого прогона прямо в `export_dir`
   (папки `_reports/` и `_applied/` не трогает), чтобы в новый архив не
   попали батчи от старой выгрузки;
2. **дёргает штатный `export`** (по умолчанию изменения, с `--full` — весь
   проект) — тот же самый код, что и кнопки выгрузки: те же `scan`/`State`,
   тот же формат батчей и тот же `max_batch_kb`;
3. **пакует все получившиеся `.txt` в один `.rar`** через WinRAR
   (`Rar.exe`, ищется в PATH и в `C:\Program Files\WinRAR\`).

Архив кладётся в `archive_dir`; если он не задан в конфиге —
в `<родитель project_root>/.codeshuttle-archives`. Имя:
`<метка времени>_<имя папки проекта>_<full|delta>.rar`. Старые архивы не
трогаются, чистится только outbox с батчами.

Один конфиг = один корень проекта. Нужен один архив на несколько модулей —
укажи корнем их общую папку; нужны отдельные архивы — два конфига и два
запуска. Кнопки в окне — зелёная «Экспорт одной кнопкой» и «Изменения →
батчи → .rar» (без git).

## Командная строка

Из cmd батник вызывай как `.\start.bat` — иначе `start` перехватывает
встроенная команда Windows. Либо напрямую:

```bash
python -m codeshuttle export --full
```

```bash
python -m codeshuttle export
```

```bash
python -m codeshuttle import
```

```bash
python -m codeshuttle status
```

Экспорт одной кнопкой (git → батчи → .rar); `--full`/`--delta` перекрывают
`ship_kind` из конфига, `--yes` — переключать ветки без вопроса (без терминала
вопрос задать некому, поэтому там `--yes` обязателен, если нужно переключение):

```bash
python -m codeshuttle ship --full
```

```bash
python -m codeshuttle ship --dry-run
```

Только fetch и проверки папок с файлом ветки, ничего не меняя:

```bash
python -m codeshuttle git-check
```

Создать файл ветки (`--manual` — не переключать самому, `--allow-dirty`,
`--remote upstream`):

```bash
python -m codeshuttle git-mark C:\work\motivation-orchestrator develop
```

Применить присланный архив (распакуется в `<inbox>/<имя архива>/`):

```bash
python -m codeshuttle import --rar C:\Downloads\20260925T101500000_work_full.rar
```

Ещё: `import --from D:\батчи` (папка мимо конфига), `import --dry-run`,
`export --dry-run`, `archive --full`, `baseline`, `init`, `gui`. Флаг
`-c путь/config.json` — свой конфиг (удобно, когда гоняешь несколько проектов).

Самопроверка на временных проектах — сквозной цикл, коллизии импорта и
git-подготовка на настоящих временных репозиториях:

```bash
python selftest.py
```

```bash
python selftest_import.py
```

```bash
python selftest_git.py
```

## config.json

```jsonc
{
  "project_root": "C:/work/my-project",   // откуда выгружаем и куда импортируем
  "export_dir":   "C:/work/_shuttle/out", // outbox
  "import_dir":   "C:/work/_shuttle/in",  // inbox
  "archive_dir":  "",                     // пусто -> <родитель project_root>/.codeshuttle-archives
  "max_batch_kb": 45,                     // потолок размера одного .txt
  "state_file":   "",                     // пусто -> .state/ рядом с инструментом
  "ship_kind":    "full",                 // экспорт одной кнопкой: full | delta
  "gui_tab":      "export",               // какую вкладку окна открыть при запуске

  "git": {
    "fetch_timeout_sec": 180,   // сколько ждать fetch одной папки
    "confirm_switch": true      // окно: спрашивать перед переключением веток
  },

  "scan": {
    "mode": "whitelist",        // whitelist = только известные расширения; all = всё текстовое
    "extensions": [...],        // что считать кодом
    "filenames":  [...],        // файлы без расширения: Dockerfile, mvnw, gradlew…
    "exclude_dirs": [...],      // ветки, которые не обходим вообще
    "exclude_globs": [...],     // маски бинарников, архивов и результатов сборки
    "keep_globs":    [...],     // принудительно включаемые файлы
    "max_file_kb": 512          // файлы крупнее пропускаются
  },

  "import": {
    "apply_deletes": true,         // применять DELETE из дельты
    "move_applied": true,          // применённые паки -> inbox/_applied/
    "prune_extra_on_full": false,  // при full-паке удалять локальные лишние файлы
    "require_all_batches": false   // true = не применять пак, если донесли не все батчи
  }
}
```

Текстовые конфиги входят в стандартный белый список расширений. `scan.keep_globs`
сильнее `exclude_globs` и белого списка и позволяет принудительно включить
конкретный файл.

> Если ты ужесточил фильтры уже после первой синхронизации, выпавшие файлы
> **не** уедут в дельту как удаления: экспорт шлёт DELETE только на то, чего
> реально нет на диске. На приёмнике старые копии просто останутся лежать.

## Как это устроено

```
codeshuttle/
  config.py     значения по умолчанию, загрузка/слияние/сохранение конфига
  scanner.py    обход дерева, технические фильтры и чтение без изменения содержимого
  packfmt.py    формат батча: рендер, разбиение на части, разбор, экранирование
  state.py      хэши файлов последней синхронизации, вычисление дельты
  exporter.py   сборка пака и запись батчей + отчёт
  archiver.py   обёртка: чистка outbox -> export -> батчи в один .rar; распаковка .rar
  gitsync.py    файлы веток: поиск, fetch, проверки, переключение/fast-forward
  ship.py       экспорт одной кнопкой: gitsync -> archiver
  importer.py   сборка файлов из батчей, проверки, запись и удаления
  gui.py        окно: вкладки «Экспорт» / «Импорт», таблица папок, журнал
  cli.py        консольный интерфейс
selftest.py        сквозная проверка: экспорт -> импорт -> дельта -> импорт
selftest_import.py коллизии импорта
selftest_git.py    git-подготовка на временных репозиториях + архив + импорт .rar
```

Состояние (`.state/state_<hash>.json`) хранит `путь -> sha256` на момент
последней выгрузки или импорта, плюс отпечаток всего дерева. Из него считается
дельта. Файл привязан к пути проекта, лежит рядом с инструментом и в git не
попадает — на каждой машине он свой.

Поле `BASE` в батче — отпечаток дерева, от которого считалась дельта. Если на
приёмнике отпечаток другой (кто-то правил файлы мимо синхронизации), в журнале
будет предупреждение, но пак всё равно применится. `RESULT` после импорта
сверяется с локальным: совпал — деревья идентичны.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| `не хватает батчей [3, 7] из 12` | Что собралось — уже применено. Донеси недостающие `.txt` в ту же папку и жми «применить» снова, доложится поверх. |
| `нет частей [4] из 4` | Файл приехал не целиком (не хватает батча с его хвостом). Наполовину он не записывается — донеси недостающий батч. |
| `не сошлась контрольная сумма` | Батч побился при копировании (обрезался, слетела кодировка). Этот файл не записан; перевыгрузи пак. |
| `дельта считалась от состояния …` | На приёмнике правили файлы мимо синхронизации. Не блокирует: применяется по факту содержимого. Если сомневаешься — выгрузи полный пак. |
| В коде появился `__REDACTED__` | Текущая версия CodeShuttle его не создаёт. Маркер уже был в исходнике либо пакет создан старой версией с санитайзером. |
| Нужного файла нет в выгрузке | Смотри `_reports/report_*.md` — там причина. Обычно расширения нет в `scan.extensions`, файл слишком большой или имя попало под техническую маску. |
| Нужно начать дельты «с чистого листа» | Кнопка «Отметить как синхронизировано» либо `python -m codeshuttle baseline`. |
| `ветки «X» нет на origin` | Опечатка в `branch` или ветку удалили. Двойной щелчок по папке в таблице — там список веток remote. |
| `fetch … не удался` | Нет сети/доступа к remote. Git запускается без вопроса о пароле, чтобы не зависнуть: один раз сделай `git fetch` в этой папке руками, чтобы сохранились учётные данные. |
| `незакоммиченные изменения` / `конфликт при переключении` | Закоммить или `git stash`, либо (если правки не конфликтуют и должны уехать) `"allow_dirty": true`. Конфликт при переключении блокирует всегда. |
| `незапушенных коммит(ов)` / `разошлась` | Выгрузка должна совпадать с remote: запушь коммиты или разберись с веткой руками. |
| `переключи сам` | В файле ветки `"checkout": "manual"`: сделай `git checkout <ветка>` и нажми кнопку снова (или поставь `auto`). |
| `репозиторий изменился после проверки` | Между проверкой и переключением кто-то закоммитил/переключил ветку. Просто нажми кнопку ещё раз. |
